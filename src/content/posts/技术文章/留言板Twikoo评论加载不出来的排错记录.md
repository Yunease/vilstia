# 起因

我的博客用 Astro 搭建，页面切换走的是 swup（客户端路由）。留言板用了 Twikoo 当评论区。某天我发现一个很邪门的现象：

**从首页点进留言板，评论区一片空白，DevTools 的网络面板里连 Twikoo 的 CDN 请求都没有。但只要一刷新（F5），评论就正常加载、正常渲染了。**

就是那种"刷一下就好"的间歇性 Bug。最烦这种了 —— 因为它"能复现，但说不清为什么"。

> 说句题外话，这 bug 差点没把我绕进去。一开始我一直往"加载时序竞争"那个方向钻，后来才发现方向错了，真正的坑在别处。这篇文章除了记下解决办法，更想记下**怎么一步步定位到它的**。

---

# 一、现象还原

先把我看到的完整现象列出来，方便后面排查：

- 首次**客户端跳转**（swup 切换）进入 `/message-board/`：评论区不渲染。
- DevTools 里那个容器长这样，看起来根本没被初始化：

```html
<div id="twikoo-container"></div>
```

- 网络面板里**完全没有** Twikoo 相关的请求（连 `twikoo.all.min.js` 都没加载）。
- **刷新页面**后一切正常：请求出现、评论区渲染。

归纳一下关键点：**客户端跳转进来 = 没反应；整页刷新 = 正常。**

这组现象其实信息量很大。它说明：不是 Twikoo 初始化失败，而是**初始化代码在"客户端跳转"这条路径上压根没跑**。因为如果初始化跑过，至少会有一次 CDN 请求。

---

# 二、第一轮排查：先怀疑"时序竞争"

因为现象是"跳转失败、刷新成功"，我最先想到的是 **swup 初始化跟 Twikoo 初始化之间有时序竞争**。

我的项目里，swup 不是简单同步初始化，而是经过一段异步加载才就绪的（要动态 import 核心、插件，最后才 `window.swup = a`）。而 Twikoo 的初始化脚本会检查 `window.swup.hooks` 是否就绪：

```js
window?.swup?.hooks ? setup() : document.addEventListener('swup:enable', setup);
```

如果 `window.swup` 还没就绪，就先监听 `swup:enable` 事件，等 swup 派发后再初始化。

我当时推测：会不会是"冷缓存下 swup 抢在 Twikoo 注册监听器之前就把 `swup:enable` 派发掉了"，导致 Twikoo 永远等不到事件？

## 2.1 这个推测的问题在哪

顺着这个方向我做了不少分析，但有一个硬伤：**`type="module"` 的脚本有严格的文档顺序执行规则**。

Twikoo 的脚本是内联模块脚本，在文档里排在 swup 初始化脚本**之后**；而 swup 真正 `enable()`（派发 `swup:enable`）是在 `window.load` 之后才异步完成的。内联模块脚本会在 `load` 之前就执行完并注册好监听器，所以正常整页加载时，Twikoo 的监听器**总是**先于 swup 派发注册好 —— 理论上是不会错过的。

也就是说，"时序竞争"这条线，**对整页加载场景解释不通**。真正有问题的，是"客户端跳转"那条路径。于是我开始往另一个方向查。

---

# 三、关键转机：怀疑 swup 的"脚本重执行"机制

既然整页加载正常、只有客户端跳转有问题，那问题大概率出在 **swup 跳转时对脚本的处理**上。

swup 跳转时只交换配置里指定的容器，我用的是：

```js
containers: ["main", "#toc"]
```

也就是说，跳转时 swup 只会把新页面的 `<main>`（和 `#toc`）换进来，**其它部分不动**。

而 swup 换进来新内容后，靠一个 `SwupScriptsPlugin` 去"重新执行"新内容里的脚本（因为通过 innerHTML 换进来的脚本浏览器不会自动跑）。这个插件会扫描文档里所有不带 `data-swup-ignore-script` 的脚本，把它们重新执行一遍。

到这里，我隐约觉得问题跟"脚本在不在 `<main>` 里"有关。

---

# 四、真相大白：脚本被 Astro"提升"到了 `<main>` 外面

我打开构建产物 `dist/message-board/index.html`，数了一下各个关键标签的位置：

```
<main    -> 第 113952 字符
</main>  -> 第 116224 字符
</body>  -> 第 129267 字符
twikoo 脚本 -> 第 129628 字符   ← 在 </html> 之后！
```

看到没有 —— **Twikoo 的初始化脚本被 Astro 输出到了 `<body>` 末尾、甚至在 `</html>` 之后**，完全落在 `<main>` 容器**外面**。

## 4.1 为什么脚本会跑出 `<main>`

我留言板页面的结构原本是这样：

```astro
<MainGridLayout>
    <!-- 标题 -->
    <!-- 留言区：里面是 <div id="twikoo-container"></div> -->
</MainGridLayout>

<script>
    // Twikoo 初始化逻辑
</script>
```

注意那个 `<script>` 是写在 `<MainGridLayout>` **组件外面**的。Astro 会处理页面里的 `<script>` 并把它**提升（hoist）到 body 末尾**去统一输出。于是：

- 留言区的 `<div id="twikoo-container">` —— 在 `<main>` 里，swup 会把它换进来。✅
- Twikoo 的 `<script>` —— 被提升到了 `<main>` 外面。❌

## 4.2 这怎么就导致评论加载不出来

这下所有现象都能解释了：

- **swup 客户端跳转**进留言板：swup 只换 `<main>`。`#twikoo-container` 这个 div 被换进来了，但**初始化脚本在 `<main>` 外面**，根本没被加进文档 → `SwupScriptsPlugin` 找不到它 → 初始化代码压根没执行 → 没请求、没渲染。
- **整页刷新**：浏览器解析整个文档，包括 `<main>` 外面的脚本 → 脚本执行 → 请求 + 渲染。

一句话：**"注释框进了门，初始化脚本却被丢在了门外。"** 这两个本该在一起的东西，一个在 swup 会交换的容器里，一个在容器外。

---

# 五、修复

找到根因，修法就简单了：**让 Twikoo 的脚本落进 `<main>` 里**，这样 swup 换容器时就能一起带进来并重新执行。

具体做法：

1. 把 `<script>` **移进 `<MainGridLayout>` 的槽内**（即进入 `<main>`）。
2. 给脚本加上 **`is:inline`** —— 关键一步。因为普通 `<script>` 还是会被 Astro 提升到 body 末尾，加了 `is:inline` 它才会老老实实待在原地。

```astro
<MainGridLayout>
    <div class="message-board-content ...">
        <div id="twikoo-container"></div>
    </div>

    <!-- 必须 is:inline + 放槽内，否则会被 Astro 提升出 <main> -->
    <script is:inline>
        // Twikoo 初始化逻辑
    </script>
</MainGridLayout>
```

改完再数一遍构建产物：

```
<main    -> 第 113952 字符
twikoo 脚本 -> 第 114914 字符   ← 现在在 <main> 里面了 ✅
</main>  -> 第 118859 字符
```

Twikoo 脚本成功回到了 `<main>` 内。客户端跳转时，swup 会连脚本一起换进来、再被 `SwupScriptsPlugin` 重新执行 → 评论正常加载。**刷新和跳转两种方式都正常了。**

---

# 六、顺手做的健壮性改进

定位过程顺便把 Twikoo 的初始化逻辑也重构了一下，让它在各种路径下都更稳：

- **`loadTwikoo()`**：负责加载 CDN + 初始化，加了 `twikooLoading` 标志防重复加载。
- **`setupSwupHooks(swup)`**：只负责绑定 swup 的 `page:view` / `content:replace` 钩子，并且按 **swup 实例引用**做幂等（`hooksBoundTo === swup` 就跳过），防止同一实例重复绑定、也防止监听器无限累积。
- **统一入口**：模块执行就立即尝试初始化一次（不押在 swup 就绪上），同时注册 `swup:enable` 兜底，再检查当前 `window.swup` 是否已就绪 —— 双保险。

> 期间我还加了一堆 `[Twikoo]` 开头的 console 日志来做验证，确认"模块到底有没有执行、swup 有没有就绪"。等定位清楚后就保留了一套最小日志，方便以后排查。

# 七、复盘与教训

## 7.1 为什么一开始没往"脚本位置"想

因为"脚本被 Astro 提升到 body 末尾"这个行为太隐蔽了。你在源码里明明看到 `<script>` 写在组件旁边，结果它跑到了文档最末尾 —— **源码位置 ≠ 输出位置**。而 swup 又是按"输出位置"来决定交换哪些容器的，两者的错位正是 bug 的来源。

> 排查这类问题的通用心法：**别只盯"初始化逻辑对不对"，要盯"初始化代码到底有没有被执行"。** 加一行日志 / 断点确认"代码根本没跑"，能省下一大堆对逻辑的猜测。

## 7.2 给同样踩坑的人

1. **先分清是"整页加载"还是"客户端跳转"出的问题** —— 这决定了排查方向完全不同。
2. 确认 bug 时先看**有没有网络请求**。连请求都没有，基本就是"初始化代码没跑"，而不是"初始化失败了"。
3. 用了 swup 这类客户端路由 + Astro，**一定要检查脚本的最终输出位置**是否在 swup 的交换容器里。Astro 会提升脚本，这个坑很隐蔽。
4. 需要留在原地、跟着容器一起被交换的脚本，记得用 **`is:inline`** 并放在对应容器内。

# 写在最后

一个看着像"时序玄学"的间歇性 Bug，最后居然是一个"脚本被提升到容器外"的静态结构问题。

如果当初被"刷新就好"的表象带偏，继续在时序竞争里打转，可能还要折腾很久。真正让我跳出来的，是那句自我反问：**"不是初始化失败，而是初始化代码压根没执行吧？"** —— 顺着这条，几分钟就找到了它。

希望这篇文章能给同样被 Astro + swup 组合坑到的朋友一点参考。
